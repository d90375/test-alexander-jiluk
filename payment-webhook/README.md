# Обработка оплаты подписки

FastAPI + PostgreSQL + SQLAlchemy/Alembic. Один эндпоинт `POST /webhook/payment`,
который принимает уведомление от банка и активирует подписку.

## Запуск

```
docker compose up --build
```

Миграции накатываются автоматически при старте контейнера, API поднимается на
`http://localhost:8000`.

Для проверки нужен пользователь в базе:

```
docker compose exec db psql -U postgres -d payments \
  -c "insert into users (email) values ('test@example.com');"
```

Отправить вебхук:

```
curl -X POST http://localhost:8000/webhook/payment \
  -H 'Content-Type: application/json' \
  -d '{"payment_id": "abc-123", "user_id": 1, "amount": 4900, "status": "CONFIRMED"}'
```

Повторная отправка того же запроса не создаст второй платёж и не сдвинет
`expires_at` — можно дёрнуть curl несколько раз и посмотреть в базу.

`query.sql` — запрос из п.4 (активные подписчики без посещений за 30 дней).

## Решения и почему

- **Дубли вебхука.** На `payments.payment_id` висит уникальный индекс, вставка идёт
  через `INSERT ... ON CONFLICT DO NOTHING`. Если вставилось 0 строк — это повтор,
  просто отвечаем 200 и подписку не трогаем. Это же закрывает гонку двух
  одновременных одинаковых вебхуков: второй запрос повиснет на блокировке индекса
  и после коммита первого увидит конфликт.
- **Падение между «записали платёж» и «дали подписку».** Запись платежа и апсерт
  подписки выполняются в одной транзакции, коммит один в самом конце. Если процесс
  умер посередине — транзакция откатывается целиком, платёж без подписки в базе
  остаться не может. Банк потом ретраит вебхук, и он обработается заново с нуля.
- **Подписка.** Считаю, что у пользователя одна строка в `subscriptions`
  (уникальный `user_id`), активация — upsert: `status = 'active'`,
  `expires_at = now() + 30 дней`, как в условии. Если нужно накапливать срок при
  оплате заранее (продление от старой `expires_at`), это меняется в одном месте.
- **Статусы.** Платёж пишу с тем статусом, который пришёл, но подписка активируется
  только при `CONFIRMED`. Исхожу из того, что `payment_id` — идентификатор
  конкретного уведомления о платеже и статус по нему не меняется; если банк умеет
  слать сначала `PENDING`, потом `CONFIRMED` с тем же `payment_id`, надо будет
  добавить обновление статуса с блокировкой строки.
- **Неизвестный `user_id`** — 404, пусть банк ретраит и это будет видно в логах,
  молча глотать такое не хочется.
- `amount` храню целым числом (в копейках), как приходит от банка.
