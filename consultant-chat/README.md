# Чат с консультантом

Next.js (App Router) + TypeScript + TanStack Query + Tailwind + Zustand. Одна
страница `/chat`: список встреч (SSR + TanStack Query) и чат поверх WebSocket с
автопереподключением и очередью неотправленных сообщений.

## Запуск

Нужны два процесса — echo-сервер и Next:

```
npm install
npm run ws     # echo-сервер из условия на :8081
npm run dev    # Next на http://localhost:3000
```

Открыть `http://localhost:3000/chat` (с корня редиректит туда же).

Если 8081 занят (например, Metro/Expo использует тот же порт):

```
WS_PORT=8082 npm run ws
NEXT_PUBLIC_WS_URL=ws://localhost:8082 npm run dev
```

Что проверить:

- **Список без JS**: отключить JavaScript в devtools и перезагрузить страницу —
  встречи видны, потому что пришли в HTML с сервера.
- **«Обновить»** перезапрашивает `/api/meetings` без перезагрузки (видно по
  времени «Обновлено» под списком).
- **Обрыв связи**: сервер сам рвёт соединение раз в ~30 секунд. В этот момент в
  шапке чата появляется «нет связи», сообщения, отправленные в оффлайне,
  помечаются «не отправлено» и уходят сами после автопереподключения (или можно
  ускорить кнопкой «Повторить»).

## Решения и почему

- **Граница server/client.** `chat/page.tsx` — серверный компонент: он делает
  `prefetchQuery(['meetings'])` и отдаёт состояние через `HydrationBoundary`,
  поэтому HTML приходит уже со списком (требование «видно без JS»). Клиентские —
  `MeetingsList` (useQuery + кнопка «Обновить»), `Chat` (WebSocket живёт только в
  браузере) и `Providers` (он держит QueryClient и оборачивает дерево в
  `layout.tsx`). Граница проходит там, где начинается интерактивность: всё выше —
  разметка и данные, которые дешевле отдать с сервера.
- **Почему hydration, а не `initialData`.** `initialData` пришлось бы
  протаскивать пропсом; dehydrate/hydrate — штатный способ TanStack Query
  передать серверный кэш клиенту. После гидрации данными владеет query-кэш, и
  «Обновить» — это просто `refetch()`.
- **Один источник данных о встречах.** `getMeetings()` в `src/lib/meetings.ts`
  читают и route handler `/api/meetings` (для клиентских рефетчей), и серверный
  префетч напрямую — ходить по HTTP в самого себя во время SSR незачем.
  На route handler и странице стоит `force-dynamic`: встречи — персональные
  данные, кэшировать ответ между запросами нельзя.
- **Подтверждение доставки поверх эха.** Сервер трогать нельзя, но формат
  сообщений — наш: шлю JSON `{id, text}`, эхо возвращает его как есть, и по `id`
  помечаю своё сообщение доставленным (эхо заодно играет роль «ответа
  консультанта»). Без `id` нельзя понять, какое из сообщений подтверждено —
  особенно если отправить два одинаковых текста подряд.
- **Оптимистичная отправка и очередь.** Сообщение попадает в ленту сразу со
  статусом «отправляется». Если сокет закрыт — сразу «не отправлено» (очередь).
  При обрыве все неподтверждённые (`pending`) тоже возвращаются в очередь: сервер
  мог их не получить. После `onopen` очередь уходит автоматически, порядок
  сохраняется. Повторная отправка безопасна: если эхо на этот `id` уже приходило,
  дубль игнорируется — второй «ответ консультанта» не появится.
- **Переподключение.** На `onclose` — реконнект с экспоненциальным бэкоффом
  (0.5с → 5с максимум), без перезагрузки страницы. Кнопка «Повторить» сбрасывает
  таймер и подключается немедленно. `onerror` отдельно не обрабатываю: у
  браузерного WebSocket за ним всегда следует `close`.
- **Почему Zustand для чата.** Колбэки сокета создаются один раз и живут всё
  соединение, а функция компонента вызывается заново на каждый рендер — через
  замыкание колбэк видел бы список сообщений на момент своего создания, и очередь
  не уходила бы после реконнекта. Добавить `messages` в зависимости эффекта
  нельзя: это пересоздавало бы сокет на каждое сообщение. В сторе эта проблема
  снимается `get()` — колбэк спрашивает состояние в момент срабатывания. То же
  самое решается связкой `useState` + зеркало в `ref`, но стор читается проще.
  Сокет, таймер реконнекта и счётчик попыток живут вне стора: это не состояние
  UI, и менять их без ререндера правильнее.
- **Стор модульный (`create()`), без фабрики и контекста.** При SSR это был бы
  синглтон на процесс, общий для всех запросов, но сокет открывается только в
  браузере, поэтому на сервере стор остаётся пустым и состояние между
  пользователями не пересекается. Если бы чат наполнялся при SSR, понадобилась бы
  фабрика с контекстом — как сделано с `QueryClient` в `Providers.tsx`.
- **Даты** форматирую с фиксированной таймзоной, чтобы серверная и клиентская
  разметка совпадали (иначе hydration mismatch при разных таймзонах сервера и
  браузера). Метка «Обновлено» — наоборот, по локальным часам: это время клика
  пользователя, а не дата из данных.

## Что можно доработать

- Обрыв ловится только по `onclose`. При «полуоткрытом» соединении (сеть пропала
  без FIN/RST) сообщение может зависнуть в статусе «отправляется» — лечится
  heartbeat'ом (ping/pong с таймаутом).
- Дедупликация эха живёт на клиенте, потому что echo-сервер из условия менять
  нельзя.
